# 表格化 Prompt 协同设计样例

> 语言：[English](../../en/requests/prompt-collaboration.md) · **中文**

> 呈现参考 · 合成设计内容 · 非实际调用记录或已批准生产方案

这里同时展示两个阶段的版式；实际协同应先等待清单确认，再一次审阅一个选定请求。
表格可按业务复杂度增减，不要求复制相同章节、请求数量或字段。

## 多轮推进与变更记录

Prompt 协同优化、Flow 流程设计、多轮实验效果评估等任务需要连续推进时，
每轮实质性回应的头部先展示当前事项表和变更记录表，再展开具体设计、修改或实验结论。

事项表采用**状态在左、事项在右**，编号跨轮保持稳定。明确体现新增、修改、移除和放弃：
*新增文字*、~~旧内容~~ → *新内容*、❌ ~~已放弃事项~~，同时使用文字状态，
不只依赖颜色或图标。区分“已确认”“待落实”“已落实”和“已验证”；
移除时说明是删除重复工作，还是放弃目标，以及保留的职责由谁承担。

变更表记录**时间及其时区、讨论版本、关联事项、变更及原因、落实状态**。
D01、D02 等只表示讨论修订，不是框架或产物发布版本。时间按实际已知精度记录，
不知道的历史时间明确标注，不补造。后续确认、落实、移除或重新打开事项时追加记录，
保留先前轨迹；提议尚未被采纳时标为待确认，沿用已有的协作授权。

以下为合成呈现样例，时间和状态仅供展示，不是实际工作证据。
这些表格服务于开发者协作，不应自动加入应用的业务模型 Prompt。

事项表只突出本轮差异，后续恢复为易读的当前表述，旧内容留在历史记录中。
每轮可展示本轮变更增量，并保留完整记录入口；没有变化时如实说明。
新证据使已完成事项失效时，明确重新打开并记录原因。

复用已有计划、审阅笔记或实验记录。短任务可直接在会话维护，长任务可借助已有项目文件
支持恢复和交接；事项多时按阶段汇总，保留未决事项和变更的可见性。
不强制另建管理系统、固定数据协议或额外审批门槛，也不为每次工具进展消息创建讨论版本。

## 1. 确认模型请求清单

**业务场景：** 将“会议行动项跟进”的产品需求整理成供产品与研发评审的设计文档。

**流程：** 产品需求 → 章节规划 → 分章节写作 → 程序组装 → 按需整体审阅。

| 请求 | 核心职责 | 产出交给谁 | 审阅状态 |
|---|---|---|---|
| **R1 · 章节规划** | 确定章节覆盖、顺序和待确认问题。 | 章节写作请求、业务用户。 | **下方展开作为示例。** |
| R2 · 章节写作 | 展开当前章节，保持必要的前文衔接。 | 程序组装。 | 后续按需审阅。 |
| R3 · 整体审阅 | 检查覆盖、矛盾和重复。 | 局部修订流程。 | 可选，尚未确定。 |

R2 是同一种请求设计，可能执行多次。程序负责内部标识、顺序、存储、结构校验和正文拼接。

**实际协同在此等待确认：请求清单及职责是否合理？需要增删或调整哪些边界？**

## 2. 单项 Prompt 明细

### R1 · 章节规划｜待确认

| 项目 | 本次设计 |
|---|---|
| **要解决什么** | 怎样组织章节，才能覆盖需求并支持后续分段写作？ |
| **做到什么程度** | 给出有序章节计划、各节范围和待确认问题。 |
| **本次不做什么** | 不生成章节正文，不虚构系统能力，不创建真实任务。 |
| **谁消费结果** | 写作请求读取章节计划；用户确认信息缺口。 |

### Prompt 主表

下表是准备提供给模型的内容；审阅标题与确认状态不会自动加入模型请求。

| Slot | 主题 | 准备发送给模型的内容 |
|---|---|---|
| **`system`** | 角色与边界 | 你是产品设计分析助手。依据当前提供的需求和事实工作，区分已知事实、设计建议与待确认事项。 |
| **`input`** | 业务背景 | 团队主要通过企业 IM 协作。会议组织者关注行动落实，参会者关注负责人和截止时间，管理者关注推进情况。 |
| `input` | 当前问题 | 会议结论分散在纪要、群消息和个人记录中，行动项在复制、确认和跟进过程中容易丢失。 |
| `input` | 预期目标 | 把“会议结论—任务确认—持续跟进”连成清晰闭环，减少人工反复追问。 |
| **`info`** | 文档用途 | 本例约定文档用于产品与研发评审，需要说明业务行为及其实现边界。 |
| `info` | 信息边界 | 当前没有指定 IM 厂商、任务系统、接口能力、权限制度和提醒政策；不得视为已确认事实。 |
| **`instruct`** | 本轮目标 | 规划覆盖当前需求的文档章节。每章提供标题和内容概要，本轮不生成正文。 |
| `instruct` | 组织原则 | 围绕业务问题和业务闭环组织章节，明确内容边界，避免重复覆盖。按便于逐段写作的顺序排列，不预设固定章节数。 |
| `instruct` | 信息不足 | 缺失信息影响重要设计决定时，在 `open_questions` 中提出具体问题。继续规划不依赖该信息的部分，不编造系统能力。 |
| `instruct` | 返回要求 | 只返回约定的 JSON。章节概要应足以指导后续写作，不能只是重复标题。 |
| **`output`** | 结构约束 | 返回 `parts` 和 `open_questions`，字段定义见下方输出表。 |

### 模型可见示例

**实际归属：** `info.examples`。**性质：** 合成示例。**作用：** 解释既有规则，不新增规则。
这不是新增 Agently slot 或 `.examples()` API。

| 解释哪条规则 | 示例输入 | 合理行为 | 不合理行为 |
|---|---|---|---|
| 信息不足时提出问题，不编造事实。 | 需求要求同步行动项，但未确定任务系统。 | 保留相关章节；必要时询问“计划对接哪种任务系统？” | 声称该系统已经支持自动创建任务。 |

仅供审阅者看的备注或输出说明样例，应另标为 **不发送给模型**。
没有需要时不强行补示例；实际示例内容不能压过规范性正文。

### 输出契约

**返回格式：JSON。**

| 字段 | 类型 | 必填 / 空值 | 含义 |
|---|---|---|---|
| **`parts`** | 数组 | 必填、非空。 | 按写作顺序排列的章节计划。 |
| `parts[].title` | 字符串 | 必填、非空。 | 章节标题。 |
| `parts[].brief` | 字符串 | 必填、非空。 | 本节覆盖的问题与内容边界。 |
| **`open_questions`** | 字符串数组 | 必填、可为空数组。 | 需要用户确认的问题。 |

### 本轮确认

| 请确认 | 检查重点 |
|---|---|
| **职责是否合适** | 有没有把后续写作或系统操作混进本次请求？ |
| **规则是否清晰** | 是否存在信息缺口、冲突或被泛化的业务特例？ |
| **示例是否必要** | 是否仅解释正文规则，而没有偷偷改变行为？ |
| **输出是否够用** | 后续写作能否据此开展？ |

**等待确认或修订 R1，之后再展示下一项。** 修订应回到真实 Prompt/config；
涉及范围或输出变化时检查受影响的流程衔接，未变化的确认结果继续保留。

本例只展示审阅形式，不是强制业务流程、schema、章节数量或固定业务政策。
